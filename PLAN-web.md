# PLAN-web — review of mvd-web

> Updated 2026-07-06 after implementation phases 0–5 (branches phase-0…phase-5). Only open items remain below; resolved findings are in the ledger at the bottom and in git history.

Overall assessment: all sixteen findings (F1–F16) and two of the big-picture items (A5 worker-RPC correlation, A8 CDN vendoring) were resolved across phases 2–5 — see the ledger. What remains open is structural: the monolith split (A1), the state/reset registry (A2), the time-fanout subscriber model (A3), and the deferred-buckets second pass (A4, half-fixed — the playhead-reset bug is gone, the re-entrant init + synthetic click remain). The TEAM_COLORS convention is still followed everywhere in JS (A7), with the same two edge nits at the CSS/ordering boundary. `static/app.js` is now 11,484 lines (deletions in P4/P5 roughly offset by the shared-helper extractions); the 45 `─── section ───` banners are intact and remain the natural module seams. New below: the deferred review of the Aim Stats tab surface (F17–F24), which was only inventoried, never reviewed, in the original pass.

## Big picture (open)

- **A1 — app.js is a monolith and should be split into ES modules.** 11,484 lines in one `<script src="app.js">` (not `type="module"`), so every function and state object is a page global. The file still has crisp internal seams (theme constants, worker bridge, hub client, summary tables, timeline graphs, chat, map renderer, map interaction, learn mode, loc graph, heatmaps, aim stats, playback — 45 `─── section ───` banners). Splitting along those exact banners into ~10 ES modules loaded via one `type="module"` entry would need no framework, no bundler (native ESM works on a static host), and would make the implicit dependency graph (who reads `timelineState`, who writes `mapState`) explicit through imports/exports. The P5 helper extractions (`makeScanlineSampler`, `attachCanvasTooltip`, `hubReplayUrl`, `lowerBoundIndex`, `renderTableRows`) make the eventual shared-utils module cheaper to carve out. Impact: extensibility.
- **A2 — state is a set of ad-hoc global stores mutated from many places, and reset is manual and drifty.** `currentResult` (app.js:83), `timelineState` (2765), `packDropsState` (2052), `weaponGraphHitState` (3508), `powerupGraphHitState` (5107), `mapState` (5999), `_wtc` (6754), `_itemsPanelState` (8968), `locGraphState` (9824), the aim-tab trio `aimPlayer`/`aimPlayersList`/`aimVictimFilter` (10745–10751), plus loose flags (`chatRendered` 4617, `precomputedFrags` 5460, `pickupsMode` 2116). `resetUIToCleanState()` (2784–2949) is a ~165-line hand-maintained wipe list that must be updated whenever any panel gains state; the `if ('controlRegions' in mapState)` guards (2930–2934) and the `typeof … !== 'undefined'` guards (2941–2947) show it has already drifted. The aim state is *not* in the wipe list — it is instead reset by `initAimStatsView` (10756–10763), which `displayResults` calls unconditionally per load (1152), so no stale-state bug results in the normal flow — but the aim panels (`#aim-weapon-tables`, chips, heatmap canvases) are also absent from the DOM wipe, so an exception anywhere in `displayResults` before line 1152 would leave the previous demo's aim tab intact while every other panel is blank. The codebase still has three reset conventions (wipe list, `resetTimelineState`, per-tab init). Suggested: give each module an `init(result)`/`reset()` pair and have `displayResults` iterate a registry, so forgetting a reset becomes structurally impossible — the aim tab already demonstrates the pattern. Impact: extensibility/correctness.
- **A3 — `setCurrentTime` fans out to every tab unconditionally.** app.js:510–522 calls `updateTimeIndicators` (which tail-calls `updateTeamStatus`), `updateMapLegend`, `updateRegionStatus`, `updateItemsPanelStatus`, `renderChatMessages`, and `renderMap` on every playhead change — including per-mousemove while scrubbing — regardless of which tab is visible; the playback loop repeats the same fan-out every 200 ms (11475–11484). P5 removed the worst per-tick costs (the double `updateTeamStatus` call and the fresh-canvas-per-player region icons, now cached in `mapState._regionIconCache`, 7378), but hidden-tab DOM rebuilds (team status tables, region status rows at 7250–7355) are still wasted work on every scrub tick. Suggested: a small subscriber model (`onTimeChange` handlers registered per tab, invoked only for the active tab, with a "stale" flag consumed on tab switch — the tab-switch handler at 699–720 already re-renders the incoming tab). Impact: performance/extensibility.
- **A4 — the deferred-buckets second pass re-enters full init paths and simulates a click** (half of the original finding — the playhead reset, F1, was fixed in P2). `applyDeferredBuckets` (289–328) still re-runs `initRegionControlData` / `displayTimelineAnalysis` / `initMapView` in full (315–317) and then does `active.click()` (321–322) to repaint the current tab. The re-run recomputes every graph prep and map precompute from scratch and clobbers interaction state the user may have set during the deferred window (e.g. `initMapView` drops a follow-player selection, `mapState.followPlayer = null` at 6280); the synthetic click re-fires `updateUrlState` and the Firefox triple-render (716–720). Suggested: split "install per-demo data" from "apply bucket-derived data" so the second pass only does the latter, and call the active tab's render function directly instead of clicking. Impact: correctness/readability.
- **A7 — TEAM_COLORS convention: followed.** Every team-coloring site checked routes through `TEAM_COLORS` indexed by `timelineState.teams` order via `getTeamOrder` (1668) — including the Aim Stats chips and weapon-table stripes (10775/10782–10783, 10941/10957–10958). Two edge nits remain: (a) `styles.css:109–110` hardcodes `#ff5050`/`#50a0ff` for `.topbar-team-a/b` instead of `var(--team-a)`/`var(--team-b)`, silently forking the CSS mirror; (b) the team *order* itself is computed in `displayResults` (1088–1091) from `teamFragTotals(demoInfo.players)`, while the scoreboard treats `match.players[].frags` as the corrected authoritative count (1317–1325) — in a telefrag-heavy demo the "winning team = index 0" color assignment could disagree with the displayed corrected totals. Consider sourcing the sort from `match.players` with demoInfo fallback.

## Low priority / nits (open, re-anchored)

- `styles.css:109–110`: `.topbar-team-a/b` hardcode `#ff5050`/`#50a0ff`; use `var(--team-a)`/`var(--team-b)` so the CSS mirror stays single-source (see A7a).
- LOS/PVS one-way colors (`LOS_STYLE`/`PVS_STYLE`, app.js:9132–9143) are red/blue by *pair order*, visually identical to the team palette while explicitly not encoding team — the comment (9126–9131) now says "debug-arbitrary" outright; consider a hue that cannot be mistaken for team identity (e.g. orange/green).
- `resetUIToCleanState` guards `weaponGraphHitState`/`powerupGraphHitState` with `typeof … !== 'undefined'` (app.js:2941–2947); both consts are defined in the same file and the function only runs post-parse — the guards are noise (folded into A2).
- Eye-height literal `22` inline in `drawVisLines` (app.js:9164–9165, comment at 9147) deserves a named constant next to `PLAYER_ORIGIN_ABOVE_FLOOR` (8382). (The `2500` u/s teleport threshold is now the named `MAX_MOVE_PER_BUCKET`, 8014 — that half is done.)
- Four separate time-axis implementations: `drawXAxisTicks` (canvas, 3261), `renderSharedTimeAxis` (DOM, 4234), `renderUnifiedAxis` (DOM, 4516–4533 — still the only one not using `pickTickInterval` (3214); its tick count is duration-based), `renderChatTimeAxisFull` (vertical, 4739–4758 — fixed 5 s ticks that get dense on long demos). At least route `renderUnifiedAxis` through `pickTickInterval`.
- `switchTab`'s triple render (immediate + rAF + 120 ms, app.js:716–720) is a documented Firefox-snapshot workaround — fine, but it also runs for tabs that don't need it (`loc-graph` triple-fits the cytoscape view, and the `aimstats` branch at 714–715 re-runs the Gaussian density images three times — see F22); consider scoping to the canvas tabs that need it.
- The Supabase anon key inline (app.js:362–363) is a public anon key so this is acceptable, but a one-line comment saying so would pre-empt the next reviewer's alarm.
- `formatDuration` (app.js:2645) renders negative times oddly (`Math.floor` of negatives); callers currently clamp, but a `Math.max(0, seconds)` inside would make it total.
- `getWeaponName` (2651) and `SEARCH_MODE_LABELS` (886) are near the code that uses them rather than the theme-constant block at the top that claims to be the "single source of truth" for constants (3–9); either move them up or soften the header comment.
- index.html's WASM-loading overlay uses a large inline `style` block (21–27) while everything else lives in styles.css; move it to a class for consistency.
- `worker.js` `logWorkerTimings` and app.js `finishLoadTiming` both re-derive loc/bsp totals with the same reduce (worker.js:101–102, app.js:157–158) — trivial, but the timing payload could carry the sums.

## Aim Stats tab (deferred review, 2026-07-06)

Scope: the `─── Aim Stats Tab ───` section (app.js:10717–11377), its HTML (index.html:907–998), the `.aim-*` CSS (styles.css:898–1131), and the analytics contract it renders (`mvd-analytics/result/aim.go`, `RESULT_SCHEMA.md` §CrosshairSamples/WeaponAim).

What's clean: the layering is right — geometry, attribution and classification live in aim.go; the JS only bins and paints. Team colors route through `getTeamOrder()`/`TEAM_COLORS` (chips 10782–10783, table stripes 10957–10958); the weapon tables use the shared `makeSortable` (10970) with the `_sortBound` guard absorbing the second load-time pass (1155); every listener is wired once behind `_aimWired` flags (10787, 10812, 11198); `escapeHtml` (quote-safe, 894–897) covers the `title` attributes and player names; the victim-filter projection `aimWeaponView` (10915–10929) matches the schema contract exactly (enemy-split fallback, per-bucket `splash = hits − direct`, `missed = shots − hits`); duel detection correctly uses the schema's per-player `mode` (10808) — the right source here, since it must match what aim.go's attribution actually did, not the F15 team-name heuristic. The tab does no work on scrub (nothing subscribes to `setCurrentTime`), and I found no dead JS or orphaned CSS in the section: every `AIM_COL` key is referenced by `AIM_TABLE_COLS`, every `.aim-*` rule has a user.

- **F17 — SSG crosshair samples are shipped but never rendered. CLOSED BY DECISION (2026-07-06): SSG stays unrendered — SG and LG panels are enough for now.** For the record: the analyzer collects crosshair-error samples for all three hitscan weapons (`aimHitscan = {sg, ssg, lg}`, mvd-analytics/analyzer/aim.go:55; `w` vocabulary "sg/ssg/lg", RESULT_SCHEMA.md:436), but `renderAimHeatmap` (app.js:10979–10982) draws only an LG and an SG block (index.html:981–995), so SSG fires appear in the accuracy tables while their crosshair samples stay invisible in the heatmap. That is now deliberate, not an oversight; the samples remain in the schema. If demand appears, the fix is to include `'ssg'` in the SG panel's sample filter (relabelled "SG/SSG") or add a third block.
- **F18 — heatmap hover read-out misaligns (and the image distorts) when the canvas is narrower than its intrinsic width.** `drawAimDensity` sizes the canvas explicitly (`style.width = W px`, W ≈ 578 for LG, app.js:11119–11126) but `.aim-density` also has `max-width: 100%` with no `height: auto` (styles.css:989–994) — in a panel narrower than W the browser shrinks the bitmap horizontally only (aspect distortion), and the mousemove handler (11199–11218) maps cursor pixels against the unscaled `ML`/`PW`, so the reported bin (and its shot/hit counts) is wrong. Fix: scale mouse coordinates by `W / rect.width` (store the CSS `W`/`H` in `canvas._aimHover`) and add `height: auto` beside the `max-width`. Impact: correctness (narrow layouts only).
- **F19 — DYaw sign convention is documented backwards in the schema; the web flip is correct.** Both result/aim.go:46–47 and RESULT_SCHEMA.md:423–424 say DYaw is "right … positive", but the derivation (analyzer/aim.go:593: bearing − aim yaw, and Quake yaw increases counterclockwise) makes **+dyaw = enemy to the left** — which is exactly why `aimOffX` negates (app.js:10735–10740, whose comment states the true convention). A consumer trusting the docs would mirror its yaw plots — or "fix" the correct web flip. Fix: correct the two Layer-2 doc sites to left-positive (pitch up-positive is accurate). Impact: docs/cross-layer correctness trap.
- **F20 — the LG `unresolved` whiff bucket is invisible, so the LG miss classes silently don't sum.** `WeaponAim.Unresolved` (result/aim.go:125, "no beam matched") has no `AIM_COL` entry and no column in `AIM_TABLE_COLS.lg` (app.js:10896–10897); when it is non-zero the LG row shows hits + miss + blocked + far < shots with no explanation — the kind of silent drop the "surface authoritative data" rule exists to prevent. Fix: an Unresolved column (plain, with a tooltip), or fold it into Miss with the tooltip naming the merge. Impact: correctness/completeness (low).
- **F21 — `renderAimWeaponTables` hand-rolls the row loop + team stripe that `renderTableRows` exists to centralise.** app.js:10952–10963 string-concats `<tr style="border-left: 3px solid …">` per row, while the shared builder (66–81) was extracted precisely to kill that boilerplate (its own comment says so) and is used by seven other tables including the dynamically rebuilt loc heatmap (10693). The aim tables build thead+tbody into a fresh `<table>`, so the helper needs to accept an element as well as an id — a two-line change. Impact: bloat/convention (low).
- **F22 — density images render on every demo load and three times per tab switch, with no dirty guard.** `initAimStatsView` runs on the load path (1152) and draws both Gaussian density images while the tab is hidden (safe — the canvas is intrinsically sized, not measured — but paid by every user whether or not they open the tab), then `switchTab`'s triple render (714–720) re-runs `renderAimStats` → sample binning + separable blur + ImageData + histogram DOM rebuild ×3 even though player and filter are unchanged. Absolute cost is small (96×64 fine grid), but all of it is redundant; render lazily on first tab visit and memo per (player, victim-filter). Impact: performance (minor).
- **F23 — column tooltips describe 'All' semantics under every victim filter.** The `AIM_COL` tooltips (10868–10893: "Fires that hit nothing", "Share of fires that connected", …) are filter-independent, but the cells are filter-projected — under Team, an RL fire that hit only enemies lands in "Missed / Fires that hit nothing" (per the schema's own per-bucket `missed = shots − hits` contract). The panel intro (index.html:941–947) explains the slicing; the headers users actually hover don't. Fix: suffix the tooltip with the active filter ("…of the selected victims") when filter ≠ All. Impact: wording (low).
- **F24 — the heatmap hover predates `attachCanvasTooltip` and could now ride it.** The bespoke native-`title` mousemove (11198–11220) was a reasonable dodge of F8 when written; P5's `attachCanvasTooltip` (4824) now exists, and native titles need a hover pause and don't live-update while the cursor moves across bins. Migration is a `hitTest` returning the bin plus a `renderHtml` — and removes the last hand-rolled canvas hover in the file. Impact: polish (low).
- Micro-nits: a victim-filter click rebuilds the weapon tables (10816) and drops the user's active column sort — capture/reapply the `makeSortable` state across the rebuild; the blur comment "edge cells replicate — they are clamp catch-alls" (11077–11078) is stale — the density image *drops* out-of-extent samples (11062–11067, only the 1-D histograms keep clamp bins).
