# PLAN-analytics — review of mvd-analytics core

> Updated 2026-07-06 after implementation phases 0–5 (branches phase-0…phase-5). Only open items remain below; resolved findings are in the ledger at the bottom and in git history.

The three problem clusters the original review found (fields missed by the time/team post-processors, fragile string matching around timing/obituaries, and the obituary/serverinfo/helper duplication) were all addressed in phases 0–5: `TestTimelineInvariants` now guards the timelineAnalysis enumerations structurally, one obituary parser and one `ResolveSlotAt` chain exist, and the dead/duplicated code is gone. What remains below is (a) a short list of surviving nits, each re-verified against the current tree, and (b) the deferred review of the aim/shots surface (`shots.go` / `aim.go` / `weaponstay.go` and their result shapes), which had never been reviewed and turns out to carry its own instances of the known disease patterns — including one output block gated on an unrelated payload opt-in and the invariant test not reaching outside `timelineAnalysis`.

## Aim/shots surface (deferred review, 2026-07-06)

> Scheduling: F17–F20 + F23 (with F21/F22 riding along) are **Phase 5.2**
> of PLAN-implementation-order.md — branch `phase-5.2` off `phase-5.1`.
> F24 (quadratic linkers) and the nits stay unscheduled.

Scope: `analyzer/shots.go`, `analyzer/aim.go`, `analyzer/weaponstay.go`, `result/shots.go`, `result/aim.go`, `result/sample.go`, the `aimPost`/`airgibsPost` post-processors, and how `duel_normalize`/`normalizeMatchRelativeTimes` handle their fields. Overall shape is good: the sound/beam fire detection is well grounded in KTX sources (fireSoundWeapon's filename table, the TE_LIGHTNING2 rationale, the dm 2/3/5 weapon-stay gate matches ktx/src/items.c:835), reconciliation is diagnostic-only as policy demands, `normalizeMatchRelativeTimes` does enumerate Shots/Projectiles/Beams/Nails times (postprocess.go:107–120, :175–179), and phase-1's duel rewrite covers Shot/ByPlayer teams and VictimKinds (duel_normalize.go:265–320). The findings below are the exceptions, each verified against code and the committed goldens.

- **F17 — The A1 invariant test guards `timelineAnalysis` only; Shots (and every other event-carrying section) is outside it.** `TestTimelineInvariants` walks `doc["timelineAnalysis"]` exclusively (invariants_test.go:70, walker at :117–135). `Shots.Shots[]` carries the same `time`/`team` JSON key conventions and is maintained by the same two hand-enumerated post-processors (postprocess.go:175–179; duel_normalize.go:265–277) — exactly the F1 disease class the test exists to catch, and the golden corpus pins whatever values are there rather than failing (the F1 lesson). `damage.events`, `messages.events`, `frags.frags`, `weaponPickups`, `backpacks` and `items[].phases` are equally unguarded; `aim` is currently safe only structurally (computed post-normalize at registry.go:360) — a chain reorder would ship silently. Fix: lift the per-stream walker to run over each top-level section that carries `time`/`team`-keyed event arrays, plus a bespoke bounds check for Aim's columnar `crosshair.t`. **(test gap)**

- **F18 — Aim's RL/GL Direct/Splash/Missed block is gated on the opt-in spatial stream it never reads; absent on every default parse.** aim.go:393 runs the block only `if streams.Projectiles != nil`, but the block body reads only `dmg` and the already-built `wagg` counters (aim.go:399–425) — the Projectiles stream is used purely as a proxy for "projectile linking ran". The proxy is wrong: linking runs unconditionally (`linkProjectiles`, shots.go:302–303) while stream *emission* is what `ctx.ShotStreams` gates (shots.go:379). Verified in the goldens (default options, no `streams.projectiles`): `1on1_speedball_mj_240426_bravado.json` has 142 of 506 rl shots with `hit:true` (proof linking ran) yet `aim.players[].weapons[rl]` has `hits:65` and no `direct`/`splash`/`missed`. Same story for the LG whiff split (aim.go:430 gates on `streams.Beams`) — but there the geometry dependency is real (matchBeam/segIntersectsHull need beam endpoints) and documented (RELEASE_NOTES v47: "the split needs streams.beams"); the deeper issue is that ShotsAnalyzer collects every beam regardless of the flag (shots.go:98) and then discards them from the Result, so a headline v47 feature only works with `-include beams`. Fix: gate rl/gl on linking evidence (any linked rl/gl fire in `res.Shots.Shots`), and consider handing the collected beams to aim via `CoreOutputs` instead of the public Result so analytics quality stops depending on a payload-size opt-in. Docs (result/aim.go:86, RESULT_SCHEMA.md WeaponAim section) say "present only when projectile linking ran", which today reads as "present only when `-include projectiles` was requested". **(correctness / API)**

- **F19 — Warmup and post-match damage leak into the RL/GL direct counts when the F18 block does run.** `dmgByPlayer` is built from `res.Damage.Events` with no time window (aim.go:113–122) and the Events log is deliberately ungated (damage.go:16–17); aim excludes warmup *shots* (aim.go:94–96) but the rl/gl direct loop counts every non-splash rl/gl damage record in the whole demo (aim.go:399–408). A warmup direct rocket therefore inflates `Direct` (the `direct > wa.Hits` clamp at aim.go:410–412 masks, not fixes) and deflates `Splash = Hits − Direct`. The SG/SSG pellet section is safe — it matches damage to each fire inside `hitscanLinkWindowMs` (aim.go:361–370). Post-normalize, warmup damage has negative `Time` and post-match damage sits past `Streams.Global.MatchEnd`, so the fix is a one-line window (`0 ≤ d.t ≤ matchEnd`) at collection. **(correctness)**

- **F20 — duel normalization fixes `Shots.VictimKinds` but not `Damage`; `aimPost` and `airgibsPost` read the un-normalized `IsTeam`.** duel_normalize.go:279–319 flips shot kinds "team"→"enemy" and folds `TeamHits` precisely because "a duel where both players happen to share a non-empty colour team classifies every hit on the opponent as team" — but the same pass never touches `result.Damage` (no reference in the file), whose `IsTeam` is computed from the raw resolved team strings (damage.go:132–133). In exactly that duel class: (a) `airgibsPost` skips every hit (`d.IsTeam` in the reject list, airgibs.go:96) so Airgibs is silently empty; (b) `aimPost` splits by `d.IsTeam` (aim.go:120), so e.g. the rl `Enemy` split reports `Direct: 0` (all direct damage lands in `directT`, then the per-bucket clamps at aim.go:417–422 zero it) while the flipped VictimKinds say every hit was an enemy hit — the two layers contradict each other inside one result. Same root cause also skews Damage's own `Given`/`GivenTeam`/Matrix aggregates (damage.go:192–204), outside this surface but worth fixing in the same stroke. Fix: extend `normalizeDuelTeams` to reclassify Damage entries in a 1v1 (non-self player pair ⇒ `IsTeam = false`, refold GivenTeam→Given, rebuild Matrix), mirroring the Shots flip and its exactness argument. **(correctness, limited to shared-team duels)**

- **F21 — shots.go missed the A3 slot-resolver consolidation.** `ShotsAnalyzer.resolveAt` (shots.go:617–631) hand-rolls the resolution chain that A3 centralized, with drift already present: it consults `ctx.Players` only when `Name == ""`, whereas `ResolveSlotAt` also backfills an empty Team from userinfo when the name did resolve (core_outputs.go:148–158). Its comment even claims it is "mirroring the resolution chain used by the damage and frag analyzers" — both of which now delegate (damage.go:216–218, frag.go:303). Fix: one-line delegation as in weapon_pickups.go:90–92. **(duplication / drift)**

- **F22 — weaponstay.go re-implements `parseInfoString` (F7 recurring).** `weaponStayDetector.OnStuffText` (weaponstay.go:32–50) hand-rolls the same `fullserverinfo` prefix/quote-strip/backslash-pair walk that phase 5 consolidated into `parseInfoString` (metadata.go:105–126), and has already drifted: `parseInfoString` skips empty keys, the copy doesn't. Note when folding: `observe` latches the first value per key in pair order while `parseInfoString` returns a last-write-wins map — semantics differ only for a duplicated key inside one info string (protocol-pathological), so a comment on the call site suffices. **(duplication)**

- **F23 — Doc drift: the result-package comments still describe the v39 "ammo" LG detection and unlinked projectiles, contradicting the (correct) RESULT_SCHEMA.md.** No `Source: "ammo"` shot has ever been emitted by the current code — the only producers are `onSound` ("sound") and `onBeam` ("beam") (shots.go:236, :257; goldens carry only those two values) — yet result/shots.go:6–8 and :26–27 document `"ammo"`, and result/shots.go:30–34 claims "Projectile fires (rl/gl/ng/sng) are left unlinked here" while `linkProjectiles` in the same analyzer populates their Hit/Victims (shots.go:299–303). The analyzer header repeats both stale claims (shots.go:12–16) and `rawShot.source`'s doc says `"sound" | "ammo"` (shots.go:61). result/aim.go references "Rocket"/"LGReach" sub-blocks that don't exist (result/aim.go:9–10, :27–28 — the fields are Crosshair/LGRamp/Weapons) and calls Dist an "eye→target-center distance" (:50) when the geometry is muzzle-based (aim.go:33–43, :581–585). README.md:410 and mvd-analytics/README.md:158 still say "+ LG cell-ammo"; mvd-api/API.md:365 lists `ammo` as a live source value. RESULT_SCHEMA.md is already right (`sound` | `beam`, :284–286, :318) — the exact lock-step failure CLAUDE.md warns about; one nit there too: the Shot field table's Hit row (:319) still says "Hitscan fire that connected" although the prose above it documents rl/gl linking. (Changelog text such as result/result.go's v39 entry is history and should stay.) **(doc drift)**

- **F24 — Quadratic scans in the linkers and beam matcher.** `linkProjectiles` scans every shot per flight (shots.go:427–438, O(flights×shots)); `linkHitscan` scans the attacker's whole damage list per fire (shots.go:495–503); `matchBeam` scans every beam per missed LG fire (aim.go:619–633). All three inputs (`a.shots` after the sort at shots.go:279, per-slot `dmgs` in event order, `Beams.T`) are time-sorted, so a `sort.Search` window / advancing cursor makes each linear. On the 4on4 goldens (≈5k shots, ≈2k beams) this is tens of millions of comparisons per demo. **(perf, cheap fix)**

- Nits: `aimHitscan` (aim.go:55) duplicates `isHitscanWeapon` (shots.go:680–682). Aim keys its tracks by *stream* names while Shots/Damage carry raw resolved names (aim.go:64–74 vs shots.go:285), so when `disambiguatePlayerName` suffixes a colliding name with `#slot` (timeline_streams.go:570) both same-named players silently lose their crosshair/LG blocks and drop out of miss attribution (`tracks[player]` misses); airgibsPost's `streamByName[d.Victim]` (airgibs.go:50–56, :98) degrades the same way — an edge case, but the failure is silent.
