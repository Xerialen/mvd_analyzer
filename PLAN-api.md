# PLAN-api — review of mvd-api and mvd-mcp

> Updated 2026-07-05 against main @ 05e2ed9 (schema v47). Originally written pre-#97; the aim/full-data endpoints and getAim MCP tool added since change several counts — re-verified throughout.

Overall assessment: both modules are small, well-layered, and pleasant to read. mvd-api keeps handlers thin (parse params → call `view.*` → write JSON), pushes all shape logic into `mvd-analytics/view`, and isolates cache mechanics behind a two-method `demoStore` interface (GetResult + #97's EnsureShotStreams), which makes the handler tests clean fakes. The democache design (two disk tiers + 4-entry LRU + per-SHA singleflight) is sound and its concurrency is essentially correct — the singleflight, LRU mutex, and `losMu`/`streamsMu` all check out under the interleavings I traced. mvd-mcp's decision to be a dumb wire shim with zero mvd-analytics imports is well argued and well executed. The real problems are: the cache never verifies downloaded bytes against the SHA it keys everything by (F1); error classification by error-string substring (F2); ~250 lines of mechanical param-parsing/query-building boilerplate across the two modules (F3, F4); unescaped model-supplied `demoId` in proxy URLs (F5); and a cluster of doc drift, most visibly the `/overview` example in API.md showing float seconds where the code emits int32 milliseconds (F6). Nothing here is an emergency; F1/F2/F5 are the ones I would fix first.

## Big picture

- **A1 — Router/middleware structure is right-sized.** `newRouter` (mvd-api/router.go:29-66) registers 29 routes — including #97's six additions (`/shots`, `/aim`, `/streams/{projectiles,beams,nails}`, `/airgibs`) — on a stdlib `ServeMux` with method+pattern matching, wrapped by exactly two middlewares (recover, access log). No framework, no indirection. Endpoint parity with the docs is still good: every route in router.go appears in mvd-api/README.md's table and API.md §4 (the new endpoints got §4.5c/4.5d/4.11c/4.13b), and I found no documented endpoint that doesn't exist (the v36-removed `/demos/{id}/map-entities` is correctly gone and correctly documented as removed at API.md:385-389).
- **A2 — Cache lifecycle is coherent but trusts the hub blindly.** `Cache.GetResult` (internal/democache/cache.go:100-111) resolves → singleflights → walks mem LRU → tier-2 gob → tier-1 MVD → hub download. Schema bumps invalidate tier 2 via the versioned path (paths.go:34-36); corrupt gobs fall through to re-parse (cache.go:165-172). Gaps: downloaded bytes are never hashed (F1), gameId resolution happens outside the singleflight (F9), and the `ctx` parameter is decorative (F10).
- **A3 — Handlers share one pipeline correctly and never recompute cached data.** Every per-demo handler goes through `resolveDemo` (handlers.go:58-78), which centralizes id parsing, store errors, cache headers, and If-None-Match. Handlers only slice the cached `*Result` through the view layer; the deliberate exceptions are lazy `/los` and #97's `EnsureShotStreams` endpoints (`/shots`, `/aim`, `/streams/*`) (F8). What *is* repeated ~40 times is the param-parse/error-write boilerplate around the view calls (F3).
- **A4 — mvd-mcp/mvd-api duplication is a deliberate trade, but drift is already visible.** The shim re-declares the REST parameter surface by hand (mcp_backend.go input structs + mcp_backend_proxy.go query builders). The no-import decision is documented and reasonable (mvd-mcp/README.md:8-16), but the hand-mirroring had drifted in three places when this was written — #97 fixed the tool-count/table mismatch, two remain (F7) — and the query-building boilerplate is compressible without adding any dependency (F4). The Supabase URL/anon-key constants are also duplicated between mvd-mcp/supabase.go:18-19 and mvd-analytics/hubfetch/hub.go:32-33 — accepted cost of the no-import rule, but worth a cross-reference comment.
- **A5 — Concurrency is fundamentally sound.** Traced interleavings that check out: (a) two goroutines racing `getOrCompute` on one SHA — `LoadOrStore` + `done` channel is correct, entry removed after compute so failures aren't cached (singleflight.go:21-35); (b) `resultLRU` fully mutex-guarded (lru.go:36-64); (c) concurrent `/los` + other read handlers on the same shared `*Result` — `ComputeLOS` writes only `Players[i].LOS/.PVS` and `Streams.LOSComputed` (analyzer/los.go:46-49, and the write sites inside the looker loop), fields no other handler reads, and all `/los` readers acquire `losMu` first so they get happens-before on those writes. (#97's `streamsMu`/`EnsureShotStreams` splice — `Streams.Projectiles/Beams/Nails` plus `Shots`/`Aim` — follows the same acquire-before-read discipline and checks out the same way.) The two soft spots are lock granularity and wasted recompute (F8) and the `lastResolved` leak (F9).

## Findings

- **F1 — Downloaded demo bytes are never verified against the SHA that keys the cache.** internal/democache/cache.go:180-192, hubfetch/hub.go:104-128. The hub-*claimed* `demo_sha256` becomes the tier-1/tier-2 cache key, the `sha:HEX` public address, and the ETag (handlers.go:72, 117) — but nothing ever computes SHA-256 over the downloaded bytes (no `crypto/sha256` anywhere in democache's non-test code; the only import is #97's shotstreams_test.go, keying a fixture). A corrupted CDN object or a wrong `demo_source_url` poisons the cache permanently under that sha, and every "immutable" cache promise built on it is then false. Fix: in `loadResult`, hash the downloaded bytes before `writeFileAtomic` and return `ErrHubUpstream` on mismatch (the CDN path is already addressed by the sha of the `.mvd.gz` bytes, so the expected value is in hand). One hash per cold download — negligible cost. *(correctness)*
- **F2 — Hub "not found" is detected by error-string substring, in two copies.** internal/democache/cache.go:138 and cache.go:285 both do `strings.Contains(err.Error(), "not found")`, coupled to the literal `"game %d not found"` in hubfetch/hub.go:96. If Supabase returns a 4xx/5xx whose body happens to contain "not found" (hub.go:88 embeds the body in the error), a hub outage is misreported as `404 demo_not_found`; conversely a wording change in hubfetch silently turns every real 404 into `502 hub_upstream`. Fix: add `var ErrNotFound = errors.New(...)` to hubfetch, wrap it at hub.go:96, and use `errors.Is` in one shared classification helper. *(correctness)*
- **F3 — Repeated param-parse/error-write boilerplate in every handler.** handlers.go: `handleBuckets` (440-502) contains six identical `x, err := parse…; if err != nil { writeError(w, 400, "invalid_param", …); return }` blocks; the same stanza repeats in `handleChat` (315-324), `handleEvents` (510-524), `handleStreamSlice` (546-560), `handleStateAt` (582-595), `handleLocTrails` (726-745), `handleRegionControl` (787-801) — roughly 120 lines of pure ceremony (30 `invalid_param` writes in the file). #97's six new handlers sidestep it only because they take no query params beyond `nails` (a `parseBool`, which can't fail). Fix: an error-accumulating reader, e.g. `type qp struct { q url.Values; err error }` with `Float/Int/CSV/LocIndex/Layout/Reducers` methods that no-op after the first error, so each handler does the reads then a single `if p.err != nil { writeError(...) }`. Same mechanism can absorb the also-repeated "view error → 400 invalid_param" tail (e.g. handlers.go:489-492, 497-500, 533-536, 569-572, 603-606, 754-757, 807-810). This is the change that makes adding endpoint #30 five lines instead of forty. *(bloat / extensibility)*
- **F4 — mvd-mcp proxy methods are 20 copies of the same skeleton.** mcp_backend_proxy.go:176-497: every method opens with `if in.DemoID == "" { return nil, errors.New("demoId required") }` (18 occurrences — #97's `GetAim` added one) and hand-builds `url.Values` with the same `if len(x) > 0 { q.Set(k, strings.Join(x, ",")) }` / `if f != 0 { q.Set(k, strconv.FormatFloat(...)) }` patterns. Fix: one `demoPath(demoID, endpoint string) (string, error)` helper (validates + escapes, see F5) plus three tiny setters (`setCSV`, `setSeconds`, `setInt`) on a `url.Values` alias. Cuts the file roughly in half and makes the per-tool code read as a spec. Do not collapse the typed Input structs — they are what the MCP SDK infers JSON Schemas from. *(bloat / readability)*
- **F5 — Model-supplied `demoId` is spliced into proxy URL paths unescaped.** mcp_backend_proxy.go:203, 210, 217, 231, 245, 252, 259, 279, 293, 310, 341, 386, 409, 432, 450, 473, 480, 496 — 18 sites (#97's getAim added :252) — all build `"/v1/demos/" + in.DemoID + "/…"`, while `in.Map` correctly gets `url.PathEscape` at line 324. `in.DemoID` comes straight from the LLM; a value containing `/`, `?`, or `#` silently reroutes the request (e.g. `"gameId:42/frags?players=x"` turns a getOverview call into a filtered frags call). Read-only API, so severity is confusion not damage — but it's a one-line fix in the `demoPath` helper of F4: `url.PathEscape(in.DemoID)` (PathEscape leaves `:` intact, so valid ids are unchanged), or stricter, reject anything not matching `^(gameId:\d+|sha:[0-9a-fA-F]{64})$`. *(correctness)*
- **F6 — API.md's `/overview` example shows seconds; the code emits int32 milliseconds.** mvd-api/API.md:226-248 (`"duration": 613.4 // seconds`, `"matchEnd": 613.4` at :231-232, `topStreaks[].start: 234.1`, `topPowerups[].start: 412.0` at :235-236) versus overview.go:21-23 (`Duration/MatchStart/MatchEnd int32`), :86-88 and :95-96 (`Start`/`Duration` int32 with `// ms` comments), assignment without conversion at overview.go:117, 130-131; the handler test stub pins `Duration: 600000` (handlers_test.go:56). #97 rewrote adjacent API.md sections (§4.5c/4.5d are new) but left the §4.2 example and the §2.1 units table (still no overview row) untouched. API.md claims its snippets are "real captured output" (API.md:12-14) — this one predates the v24 float-seconds→ms migration (commit 6487366). Fix: recapture the §4.2 example in ms (and add overview to the §2.1 units table), or — if the intent is that the overview is a "view envelope" and should follow the seconds rule — convert in `BuildOverview` and bump the schema. Either way, today a frontend written against API.md misreads overview times by 1000×. *(correctness of docs)*
- **F7 — mvd-mcp has drifted from the REST surface in two visible places (a third was fixed by #97).** (a) `GetBackpacksInput.Weapon` is a single `string` documented "'rl' or 'lg' (single-weapon filter)" (mcp_backend.go:173, forwarded at mcp_backend_proxy.go:290-292) while REST `/backpacks` takes a CSV set since v36 (API.md:79-81; handlers.go:364 uses `parseCSV`). (b) `GetEventsInput.Types`'s schema description (mcp_backend.go:79) and mvd-mcp/README.md:313 omit the opt-in `damage`, `telefrag`, `stomp` types that API.md §4.8 documents (API.md:396-407) — the model can't discover them from `tools/list` even though getDamage's description references them. (c) **[fixed by #97]** the tool count/table mismatch is gone: mvd-mcp/README.md:33 "Twenty-one tools" now matches the 21 tools registered in mcp_tools.go (getAim included), the pinned `TestMCP_ListTools` (mcp_tools_test.go:159-166), and the README table at :41-63 (`getLocTable` present now). Fix for the rest: make Weapon `[]string` and extend the types description. *(correctness of docs / extensibility)*
- **F8 — `/los` lazy compute: one global mutex, and the work evaporates on LRU eviction.** router.go:15-19 + handlers.go:624-626: `losMu` is server-wide and held for the entire `ComputeLOS` pass ("a few seconds on a large 4on4" per API.md:533), so a `/los` request for demo B queues behind demo A's raycast. Separately, the computed LOS lives only on the in-memory `Result`, which sits in a 4-entry LRU (cache.go:83) — five distinct demos later, the next `/los` re-decodes the gob and re-runs the whole pass. #97 repeats the pattern with a heavier body: `streamsMu` (router.go:21-24) is likewise server-wide and held across `EnsureShotStreams` (handlers.go:657-659), which on a cold demo runs the full `GetResult` (hub download + parse) *plus* a second complete parse of the MVD with the stream flags on (cache.go:220-274); the spliced Projectiles/Beams/Nails and the rebuilt Shots/Aim also live only on the in-memory Result, so eviction discards that re-parse too. Fix: key the locks per SHA (a `sync.Map` of mutexes, or reuse democache's singleflight shape), and consider persisting the computed LOS/streams to a side gob (`los/v<N>/<sha>.gob`) or bumping `MemoryLRU` — the handlers currently recompute what a cache tier should hold. *(quality / performance)*
- **F9 — `lastResolved` leaks, and gameId resolution stampedes outside the singleflight.** cache.go:148 stores `sha → *GameInfo` on every hub resolve; the only drain is `LoadAndDelete` on the download path (cache.go:277). When the resolved demo is then served from the mem LRU / tier-2 / tier-1 (e.g. the `index/games` dir was wiped but results survive), the entry stays in the `sync.Map` forever — small, but unbounded over process life. Also, `resolveSHA` runs before `getOrCompute` (cache.go:103-110), so N concurrent cold requests for the same gameId issue N parallel `Hub.Resolve` calls; only the download/parse is deduplicated. Fix: drain `lastResolved` unconditionally at the top of `loadResult`, and either move resolution inside a gameId-keyed singleflight or accept the stampede with a comment. *(correctness — leak; minor)*
- **F10 — `GetResult`'s context is decorative.** cache.go:100 accepts `ctx`, but `Hub.Resolve`/`Hub.Download` take no context (hubfetch/hub.go:69, 104) and `defaultParse` discards it (cache.go:58: `_ context.Context`); `EnsureShotStreams` (cache.go:220) does the same for its re-parse. A disconnected client cannot cancel a multi-second hub download or parse. Given the singleflight shares one computation among waiters, running to completion is arguably the *right* semantics (the first caller's cancellation must not poison other waiters) — but then the signature is misleading. Fix: either thread `context.WithoutCancel`-based detachment deliberately and document it, or drop `ctx` from `ParseFunc` and add a comment on `GetResult` stating that work always runs to completion. *(readability / API honesty)*
- **F11 — Two styles for the same 422 "unavailable" rule.** `handleFrags`/`handleDamage` rely on `view.ErrUnavailable` via `writeUnavailable` (handlers.go:93-104, 220-222, 248-252), while `handleMetadata`/`handleDemoInfo`/`handleLocGraph`/`handleRegionControl` do inline nil-field checks with hand-rolled 422s (handlers.go:176-181, 341-346, 192-197, 782-785) — and #97's `handleShots`/`handleAim`/`handleAirgibs` joined the inline camp (267-272, 288-293, 824-828), which now outnumbers `writeUnavailable` seven handlers to two. Both implement the documented R3 rule, but a new endpoint author has two patterns to choose from and the availability predicate for the nil-check group lives in the HTTP layer instead of the shared view layer (WASM/CLI consumers of those sections don't get the same check). Fix: give the view layer `Metadata/DemoInfo/LocGraph` accessors that return `ErrUnavailable`, and make every handler use `writeUnavailable`. *(extensibility / consistency)*

## Low priority / nits

- cache.go:12-13 package doc: "exclusively consumed by qwanalytics/cmd/qw-mvd; it does not appear on the public qwanalytics API" — stale on both counts; the consumer is mvd-api. (Similarly stale, adjacent module: hubfetch/hub.go:12-13 "exists for the golden test harness".)
- handlers.go:423-425: `csvSetLower` doc says "csvSetLower is csvSet with each token lowercased" but no `csvSet` exists anywhere; also the helper lives in handlers.go while its only caller is map_handlers.go:75-76 — move it there.
- map_handlers.go:74-76 uses `q.Get("types")`/`q.Get("kinds")` instead of `ciGet`, so the API.md §2.2 "parameter names are case-insensitive" promise doesn't hold on `/v1/maps/{map}/entities` (`?Types=` is silently ignored).
- handlers.go:151: `setCacheHeaders` on the POST `/v1/demos/{id}` response sets `Cache-Control: public, max-age=86400, immutable` + ETag — meaningless-to-misleading on a POST; keep only `X-Cache`/`X-Schema-Version` there.
- handlers.go:70 + 40-45: `setCacheHeaders` runs before availability checks, so 422 bodies go out with `ETag`/`X-Cache`/immutable-era headers still set (writeError only overrides `Cache-Control`). Harmless with `no-store`, but an ETag on an error response is odd; consider deferring `setCacheHeaders` until success, or stripping in `writeError`.
- handlers.go:633-643: on a demo with `Streams == nil`, `/los` returns `{"players":null}` where API.md §4.11b promises a players array — initialize `out.Players = []losPlayer{}`.
- handlers.go:73: If-None-Match matched by `strings.Contains` — accepts weak validators and accidental substrings; now three copies of the same match (resolveShotStreams at :666, `writeStaticHeaders` at map_handlers.go:117). Fine in practice; an exact token compare in one helper would be stricter.
- resolveDemo's 304 check runs after `GetResult` (handlers.go:65-76), so a revalidation of an evicted/cold demo triggers a full gob decode — or, for an uncached demo, a hub fetch + parse — just to answer 304. For `sha:` ids the ETag is derivable from the id + `CurrentSchemaVersion` without touching the store.
- params.go:20-24: when a caller sends two different-case spellings of one param, the fallback winner is map-iteration random per request. Document "undefined" or prefer sorted order.
- middleware.go:53-61: `clientIP` trusts the first `X-Forwarded-For` entry unconditionally — fine for a log-only field, but worth a comment that it's spoofable and must never become an auth/rate-limit input.
- handlers.go:838-849: `recoverMiddleware` lives in handlers.go while the other middleware is in middleware.go; its `writeError` after a partial write is a silent no-op (inherent to net/http, acceptable).
- mcp_backend_proxy.go:117-121: the `errors.As(err, &netErr)` branch in `shouldRetry` is dead — both branches return true. Delete it or make non-net errors non-retryable.
- mcp_backend.go:159-160: `GetChatInput` comment says chat kinds are `say`/`teamsay`; the actual tokens (and the jsonschema on :166) are `chat`/`teamsay`.
- mvd-mcp/README.md:319-331: getStreamSlice section omits the `loc` param that `GetStreamSliceInput` (mcp_backend.go:90) supports; the input-schema sections also skip `getMapEntitiesByMap` and `getLocTable` entirely.
- mvd-mcp/supabase.go:79: `players_fts=fts.'…'` wraps a `url.QueryEscape`d value in literal apostrophes — works (tests pin it), but a player name containing `'` becomes `%27` *inside* PostgREST quoting; add a comment or a test for the apostrophe case.
- `/los` is REST-only with no MCP tool, and unlike `/geometry` (whose omission is called out at API.md:696) this is not documented anywhere. #97 widened the asymmetry: `/aim` got getAim but `/shots`, `/streams/*`, and `/airgibs` are REST-only too — either add tools (los/shots outputs are compact, LLM-friendly) or note the omissions in API.md and mvd-mcp/README.md.

## New since this review (#97–#102, not covered above)

- #97 (schema v39–43) added six REST endpoints — `/shots`, `/aim`, `/streams/{projectiles,beams,nails}`, `/airgibs` — and the `getAim` MCP tool, with matching docs (API.md §4.5c/4.5d/4.11c/4.13b, README table rows, mvd-mcp README §getAim). #98–#102 (v44–47) changed shot/aim *semantics* only; the HTTP surface is untouched since #97.
- `resolveShotStreams` (handlers.go:651-671) is a near-verbatim copy of `resolveDemo`'s tail (mapStoreError, setCacheHeaders, ETag build, If-None-Match) — the F3 helper is the natural place to fold both.
- `streamsMu`/`EnsureShotStreams` re-runs the F8 pattern with a heavier body (global mutex held across a hub download + two full parses; work lost on LRU eviction) — folded into F8 above.
- `GetAim` is the 20th F4 skeleton copy and adds the 18th unescaped `in.DemoID` splice (F5); `handleShots`/`handleAim`/`handleAirgibs` extend F11's inline-422 camp.
- Docs drift, F7 family: `aim_unavailable` / `shots_unavailable` (handlers.go:268, 289) appear only in §4.5c/4.5d prose — the API.md §2.4 error-code table (API.md:141-156) was not extended.
- Quiet degrade: when tier-1 MVD bytes are missing, `EnsureShotStreams` silently returns the lean Result (cache.go:238-243), so `/aim`/`/shots` serve data without the stream-derived parts (RL/GL splash, LG whiff split) with no signal to the caller — sits uneasily next to the repo's "surface authoritative data" rule; deserves at least a comment-grade justification or a response marker.
- API.md example payloads still say `"schemaVersion": 36` (API.md:216, 228, 644) against a current v47 — cosmetic, but it feeds the same "real captured output" promise that F6 leans on.
