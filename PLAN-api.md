# PLAN-api — review of mvd-api and mvd-mcp

> Updated 2026-07-06 after implementation phases 0–5 (branches phase-0…phase-5). Only open items remain below; resolved findings are in the ledger at the bottom and in git history.

Overall assessment: both modules remain small, well-layered, and pleasant to read, and the phase 3/5 work landed the hardening this review originally asked for — downloaded bytes are SHA-verified before caching, hub errors are classified by identity, model-supplied demo ids are validated + escaped, the server-global `losMu`/`streamsMu` became per-SHA `KeyedMutex`es, and the ~250 lines of param/proxy boilerplate collapsed into the `qp` reader and `demoPath`/`query` helpers. What remains open splits three ways: (1) the deferred persistence half of F8 (lazy LOS/stream computes still evaporate on LRU eviction — DAG Stage 3); (2) a new cluster of **hosted-exposure** findings from the deferred deep review of the #97 aim/full-data surface and democache (F12–F19 below) — the standouts are the nails-latch breaking response determinism under an immutable ETag (F12) and the complete absence of disk quota / compute throttling on an unauthenticated cache-warming endpoint (F14/F15); and (3) a tail of still-true nits, each re-verified against current code. Scheduling (decided 2026-07-06): F12/F13 were fixed in **Phase 5.3** (branch `phase-5.3`) — see the ledger; the hosted-exposure cluster F14/F15/F16/F17 (+ F19) stays a prerequisite for public hosting but hosting is **not imminent**, so it is deferred to a dedicated **hosting-prep phase** run immediately before any public deployment (see PLAN-implementation-order.md).

## Big picture (still true, re-verified)

- **A1 — Router/middleware structure is right-sized.** `newRouter` (mvd-api/router.go:28-66) registers 29 routes on a stdlib `ServeMux`, wrapped by exactly two middlewares (recover, access log). Endpoint parity with the docs holds: every route appears in mvd-api/README.md's table and API.md §4, and no documented endpoint is missing from the code.
- **A2 — Cache lifecycle is coherent; the remaining structural gap is growth, not correctness.** `Cache.GetResult` (internal/democache/cache.go:121-141) resolves → singleflights → mem LRU → tier-2 gob → tier-1 MVD → hub download, now with SHA verification on download (cache.go:226-233) and identity-based error classification (cache.go:346-356). Schema bumps invalidate tier 2 via the versioned path (paths.go:34-36); corrupt gobs fall through to re-parse (cache.go:203-209). What the lifecycle still lacks is any bound on disk or old-schema garbage collection (→ F14).
- **A3 — Handlers share one pipeline and the boilerplate is gone.** Every per-demo handler goes through `resolveDemo` (handlers.go:58-75) or `resolveShotStreams` (handlers.go:613-637), which share the conditional-GET tail via `revalidated` (handlers.go:81-88); params flow through the error-accumulating `qp` reader (params.go:137-213) and all nine availability-gated sections route through `view` accessors + `writeUnavailable` (mvd-analytics/view/availability.go, handlers.go:108-114).
- **A4 — mvd-mcp/mvd-api duplication remains a deliberate, documented trade.** The shim still re-declares the REST parameter surface by hand (mcp_backend.go input structs), now compressed through `demoPath` + the `query` setters (mcp_backend_proxy.go:30-38, 197-236). The Supabase URL/anon-key constants are still duplicated (mvd-mcp/supabase.go:17-19 vs mvd-analytics/hubfetch/hub.go:32-36); both blocks cite mvd-web/static/app.js as the shipped origin, but neither cross-references the other — still worth the one-line comment if either is ever rotated.
- **A5 — Concurrency remains fundamentally sound.** Re-traced after P3/P5: the singleflight `LoadOrStore` + `done` channel is correct for the normal path (singleflight.go:21-35); `resultLRU` is fully mutex-guarded (lru.go:36-64); `KeyedMutex` reference-counts and reclaims entries correctly (keyedmutex.go:29-52, `-race` tested); the `EnsureShotStreams` splice and `/los` `ComputeLOS` write disjoint fields and every reader of the spliced fields (`Shots`, `Aim`, `Streams.{Projectiles,Beams,Nails}`) acquires the same per-SHA lock first via `EnsureShotStreams`, so happens-before holds — I found no unsynchronized reader of those fields anywhere in mvd-api or view. The two new soft spots found in the deferred review are the singleflight panic path (F13) and the nails-latch determinism hole (F12).

## Open findings (pre-phase remnants)

- **F8b — the persistence half of F8: lazy LOS/shot-stream computes still evaporate on LRU eviction.** The lock half was fixed in P3 (per-SHA `losLocks` at router.go:23 / handlers.go:585, `shotLocks` at cache.go:88); but the computed LOS and the spliced Projectiles/Beams/Nails + rebuilt Shots/Aim still live only on the in-memory Result in a 4-entry LRU (cache.go:96, 107), and the on-disk gob stays lean by design (API.md §4.11c). Five distinct demos later, the next `/los` re-runs the raycast pass and the next `/shots` re-parses the full MVD. Deferred to DAG Stage 3 (side-gob persistence / cache-tier for derived passes) per PLAN-implementation-order — the nails-latch determinism question F12 raised is settled (Phase 5.3: one variant, nails folded into the base rebuild), so persisting the latches is now safe. *(quality / performance)*

## Low priority / nits (each re-verified against current code, 2026-07-06)

- handlers.go:444-459: `csvSetLower` doc still says "csvSetLower is csvSet with each token lowercased" but no `csvSet` exists anywhere; the helper still lives in handlers.go while its only callers are map_handlers.go:75-76 — move it there.
- map_handlers.go:74-76 still uses `q.Get("types")`/`q.Get("kinds")` instead of `ciGet`, so the API.md §2.2 "parameter names are case-insensitive" promise (API.md:71) doesn't hold on `/v1/maps/{map}/entities` (`?Types=` is silently ignored).
- handlers.go:173: `setCacheHeaders` on the POST `/v1/demos/{id}` response still sets `Cache-Control: public, max-age=86400, immutable` + ETag — meaningless-to-misleading on a POST; keep only `X-Cache`/`X-Schema-Version` there.
- handlers.go:70 + 40-45: `setCacheHeaders` runs before availability checks, so 422 bodies still go out with `ETag`/`X-Cache` set (writeError only overrides `Cache-Control`). Harmless with `no-store`, but an ETag on an error response is odd; defer `setCacheHeaders` until success or strip in `writeError`.
- handlers.go:594-604: on a demo with `Streams == nil`, `/los` returns `{"players":null}` — now contradicted by the handler's own doc comment ("Returns 200 with a players array", handlers.go:575-577) as well as API.md §4.11b's example. Initialize `out.Players = []losPlayer{}`.
- If-None-Match matching by `strings.Contains`: P5 folded the demo-path copies into one `revalidated` helper (handlers.go:83) but a second copy remains in `writeStaticHeaders` (map_handlers.go:117), and both still accept weak validators, accidental substrings, and mishandle `*`. Fine in practice; an exact token compare in one shared helper would be stricter.
- resolveDemo's 304 check still runs after `GetResult` (handlers.go:65-71), so revalidating an evicted/cold demo pays a gob decode — or a hub fetch + parse — just to answer 304. For `sha:` ids the ETag is derivable from the id + `CurrentSchemaVersion` without touching the store.
- params.go:13-14, 19-25: the `ciGet` comment now claims "the first key that matches case-insensitively wins", but the fallback iterates a Go map, so when a caller sends two different-case spellings of one param the winner is random per request. Document "undefined" or iterate in sorted order.
- middleware.go:53-61: `clientIP` trusts the first `X-Forwarded-For` entry unconditionally — still fine for a log-only field, but worth the spoofability comment now, because F15's rate limiting must *not* naively key on it (first-hop XFF is attacker-controlled unless a trusted proxy overwrites it).
- handlers.go:771-784: `recoverMiddleware` still lives in handlers.go while the other middleware is in middleware.go; its `writeError` after a partial write is a silent no-op (inherent to net/http, acceptable).
- mcp_backend_proxy.go:140-144: the `errors.As(err, &netErr)` branch in `shouldRetry` is still dead — both branches return true. Delete it or make non-net errors non-retryable.
- mcp_backend.go:159-160: `GetChatInput` doc comment still says chat kinds are `say`/`teamsay`; the actual tokens (and the jsonschema at :166, which is correct) are `chat`/`teamsay`.
- mvd-mcp/README.md:319-331: the getStreamSlice input table still omits the `loc` param that `GetStreamSliceInput` (mcp_backend.go:90) supports; the input-schema sections still skip `getMapEntitiesByMap` and `getLocTable` entirely (both are in the tool table at :55/:62 but have no `####` section).
- mvd-mcp/supabase.go:79: `players_fts=fts.'…'` still wraps a `url.QueryEscape`d value in literal apostrophes — works (tests pin it), but a player name containing `'` becomes `%27` *inside* PostgREST quoting; add a comment or a test for the apostrophe case.
- REST-only/MCP asymmetry still undocumented: `/los`, `/shots`, `/streams/*`, and `/airgibs` have no MCP tools, and unlike `/geometry` (whose omission is called out at API.md:718 and README.md:84) none of these are noted anywhere. `/los` and `/shots` outputs are compact and LLM-friendly — either add tools or note the omissions in API.md and mvd-mcp/README.md.

## Aim/full-data API + democache (deferred review, 2026-07-06)

Scope: the #97 surface (`/shots`, `/aim`, `/streams/{projectiles,beams,nails}`, `/airgibs`, their API.md sections, the `getAim` MCP tool) and all of `internal/democache` (cache.go end-to-end post-P3/P5, keyedmutex.go, singleflight.go, lru.go, paths.go, util.go), weighted for public hosting.

What checks out: the handler side of #97 is clean — all four full-data endpoints funnel through `resolveShotStreams` → `EnsureShotStreams`, availability routes through the shared view accessors, the degrade path (`X-Shot-Streams: unavailable` + `no-store`, CacheMeta.ShotStreamsUnavailable, cache.go:290-299) is well-commented, documented in API.md §4.5c/4.5d/4.11c and README.md:49, and tested (shotstreams_test.go, handlers_test.go). Locking is correct: the shot-stream need-check sits inside the per-SHA lock (no TOCTOU, cache.go:280-287), `KeyedMutex` reclaims entries, path handling is traversal-safe (`isValidSHA` before `sha[:2]`, `sanitizeMapName`), tier writes are atomic, and the `getAim` tool description is accurate and thorough (mcp_tools.go:77). The findings:

- **F14 — no disk quota, eviction, or GC on the cache root.** Tier-1 MVDs (~MBs each), tier-2 gobs, and the gameId index grow monotonically (paths.go — no delete path exists anywhere in democache), and every schema bump orphans the entire previous `results/v<N>/` tree forever. Combined with the unauthenticated `POST /v1/demos/{id}` warm-up endpoint (handlers.go:161-180), a public deployment lets anyone fill the disk by iterating hub gameIds. Needs a size-capped store or periodic GC (LRU by atime is fine — everything is reconstructible) plus an old-schema-version sweep, before hosting. *(hosted exposure — high for public hosting, non-issue locally)*
- **F15 — no global throttle on downloads/parses, and no rate limiting at all.** The per-SHA singleflight (cache.go:138) and KeyedMutex dedupe work *per demo*; N concurrent cold requests for N distinct demos run N parallel hub downloads + full parses, and each `/aim`-family cold hit adds a *second* full parse (cache.go:301-308) — unbounded CPU + allocation spikes driven by unauthenticated traffic. serve.go:37-43 wires no limiter middleware, and the only client identity available (clientIP, middleware.go:53-61) is spoofable via XFF. For public hosting: put a weighted semaphore around the download+parse and rebuild paths (bounding memory too — mvdBytes + built Result per rebuild), and front with a reverse proxy that enforces rate limits and normalizes XFF. *(hosted exposure — high for public hosting)*
- **F16 — hubfetch reads unbounded upstream bodies.** `fetch` does `io.ReadAll` with no size cap (hubfetch/hub.go:147-157), and F1's hash check runs only after the whole body is in memory (cache.go:231). A broken or hostile upstream — the CDN, or the hub-supplied `demo_source_url` fallback (hub.go:130-135) — can OOM the process with one response. Wrap in `io.LimitReader` with a generous demo-sized cap (tens of MB) and reject larger. *(hosted exposure / robustness — medium)*
- **F17 — no CORS story.** No `Access-Control-*` header is set anywhere in mvd-api, yet API.md positions the API as an HTTP integration surface for frontends. A browser app on another origin cannot call a hosted instance at all. Either add a permissive CORS middleware (safe: the API is read-only, unauthenticated, and the Bearer "label" is non-secret by design) or document that a fronting proxy must inject the headers. *(hosted exposure — medium, if browser consumers are intended)*
- **F18 — degrade/meta interactions are slightly off.** (a) `EnsureShotStreams` returns `GetResult`'s meta unchanged (cache.go:268-287), so a first-time stream rebuild that runs a multi-second re-parse reports `X-Cache: HIT` — misleading in the access log's `cache` field and to clients timing requests; consider a meta flag for "rebuilt this request". (b) On the degraded path, a conditional GET still 304s against the strong ETag (handlers.go:625-635 sets the marker before `revalidated` — deliberate, per the comment) — but that tells a client holding the *full* cached body that its copy is current *and* degraded simultaneously; a fresh GET would return a leaner body under the same ETag. Consider a distinct (or absent) ETag for degraded responses. *(observability / HTTP semantics — low)*
- **F19 — internal error text leaks to clients.** `mapStoreError`'s default branch and `writeUnavailable`'s 500 branch echo `err.Error()` into response bodies (handlers.go:99, 113), and those errors can embed local cache paths (`write tier-1: …`, cache.go:234-236; writeFileAtomic errors carry full paths, util.go:90-115) and upstream URLs. Standard practice for a hosted service: log the detail, return a generic message + request id for 5xx. *(hosted exposure — low)*
